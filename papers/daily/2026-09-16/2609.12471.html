问题的初衷（Why - 为什么要做这个研究） ​

【问题的初衷】近年来，基于大语言模型（Large Language Model, LLM）的 GPU 内核（Kernel）自动生成与优化取得了显著进展，但绝大多数工作都围绕 NVIDIA 的 CUDA 生态展开，例如 KernelBench、TritonBench 等基准与数据集几乎全部面向 NVIDIA GPU。与此同时，AMD 的 CDNA 架构 GPU（如 MI250、MI300 系列）在高性能计算（High Performance Computing, HPC）和人工智能（Artificial Intelligence, AI）训练推理中扮演着越来越重要的角色，其软件栈 ROCm 与 HIP 编程模型却严重缺乏大规模、经过执行验证的内核语料与配套的智能体（Agent）训练框架。这导致两个核心问题：第一，现有 LLM 内核智能体在生成 AMD 内核时缺乏高质量参考数据，往往需要反复调用前沿闭源大模型进行生成、反思与优化，成本高昂且难以复现；第二，AMD 平台上的内核正确性、编译通过率与延迟性能缺乏统一的评测基准，研究者无法公平比较不同方法。因此，构建一个面向 AMD CDNA GPU 的大规模、执行验证过的 HIP 与 Triton 内核语料库，并配套可训练的智能体流水线，成为推动 AMD 生态下 AI 辅助内核优化研究的关键基础设施，这正是本文 AMDKernelVault 的核心动机。

问题的解决（What - 提出了什么方案） ​

【问题的解决】论文提出了 AMDKernelVault，一个面向 AMD CDNA GPU 的开放 HIP 与 Triton 内核语料库及训练框架。其核心思路是：不再依赖反复调用前沿闭源 LLM，而是通过自建的智能体驱动流水线 HIPKernelGen 与 TritonKernelGen，将 PyTorch 参考实现自动转换为 HIP 或 Triton 内核，并在 ROCm 环境下完成编译、正确性验证与延迟剖析（Profiling），从而批量生产高质量、可执行的内核样本。语料库包含 62,153 个执行验证的 HIP 内核样本、2,377 条来自 ROCm Libraries 的生产级问答（QA）条目以及 39,893 个 Triton 内核。为验证语料库的实用价值，作者使用监督微调（Supervised Fine-Tuning, SFT）与执行感知强化学习（Execution-aware Reinforcement Learning, RL）训练了 Qwen3-8B 模型。与现有方法依赖闭源前沿模型不同，本文的本质创新在于：一是构建了首个大规模 AMD 专用内核语料库，二是将内核生成、编译、验证、剖析整合为可复现的智能体流水线，三是通过开源模型训练证明语料库可显著提升 AMD 内核生成能力，在固定评测预算下于 PyTorch-to-HIP、TritonBench-G 与 ROCmBench 上取得最高正确率。

技术方法详解（How - 怎么实现的） ​

【技术方法详解】论文的技术方法可从数据构建、智能体流水线、训练策略与评测四个层面展开：

  • 数据来源与语料构建：从 PyTorch 参考算子出发，覆盖常见张量运算与深度学习算子，通过 HIPKernelGen 与 TritonKernelGen 两条流水线分别生成 HIP 与 Triton 内核，并在 ROCm 上执行验证，最终形成 62,153 个 HIP 样本、39,893 个 Triton 样本及 2,377 条 ROCm Libraries QA 条目。
  • 智能体驱动生成流水线：HIPKernelGen 与 TritonKernelGen 将 PyTorch 参考实现作为输入，由智能体完成代码生成、编译、错误修复与迭代优化，编译与验证均在 ROCm 环境下进行，确保样本可执行。
  • 执行感知强化学习：在 SFT 基础上引入执行感知 RL，奖励信号不仅考虑文本相似度，还结合编译是否通过、执行是否正确以及延迟表现，使模型学习到真正可运行且高效的内核。
  • 延迟剖析与性能标注：每个候选内核在 AMD 硬件上进行延迟剖析，记录执行时间等指标，为后续性能优化研究提供标注数据。
  • 固定预算评测协议：在 PyTorch-to-HIP、TritonBench-G、ROCmBench 三个基准上，以固定评测预算比较不同模型，报告 Pass@1 与 Corr@3 等指标，保证公平性。
  • 开源发布：语料库与文档发布于 Hugging Face，训练与内核生成代码发布于 GitHub，便于社区复现与扩展。

核心公式与算法 ​

【核心公式】论文未给出显式数学公式，但其执行感知强化学习的奖励可形式化表示为：

R=α⋅Rcompile+β⋅Rcorrect+γ⋅Rlatency

其中 Rcompile 表示编译是否通过的奖励，Rcorrect 表示执行正确性奖励，Rlatency 表示延迟性能奖励，α,β,γ 为权重系数。

评测指标 Pass@1 可表示为：

Pass@1=1N∑i=1N1[kerneli 正确]

其中 N 为任务数，1[⋅] 为指示函数。Corr@3 表示在 3 次采样中至少一次正确的比例。

具体技术细节示例（How in Action - 算法如何执行） ​

【具体技术细节示例】假设输入为一个 PyTorch 参考实现：y=ReLU(x)，其中 x 为形状 [1024,1024] 的 FP16 张量。

第一步，智能体选择目标语言为 HIP，HIPKernelGen 生成候选内核，例如一个包含全局内存加载、max(x,0) 计算与写回的 HIP 核函数。

第二步，在 ROCm 环境下编译该候选内核。若编译报错，例如缺少头文件或线程索引越界，智能体读取错误信息并反思修复，重新生成候选，直至编译通过。

第三步，执行正确性验证：将 HIP 内核输出与 PyTorch 参考输出逐元素比较，若最大误差超过阈值（如 10−3），则判定不正确，返回修复；若通过，则进入下一步。

第四步，延迟剖析：在 AMD GPU 上多次运行该内核，记录平均执行时间，例如 Tkernel=0.12ms，并与 PyTorch 原生实现对比。

第五步，将样本写入 AMDKernelVault，包含 PyTorch 参考、HIP 内核源码、编译日志、正确性结果与延迟数据。

第六步，在训练阶段，该样本用于 SFT，并在执行感知 RL 中根据编译通过、正确性与延迟计算奖励 R=αRcompile+βRcorrect+γRlatency，更新 Qwen3-8B 参数。最终模型在 PyTorch-to-HIP 基准上对类似 ReLU 任务可达到 34.0% 的 Pass@1。

实验结果（Results - 效果如何） ​

【实验结果】论文在三个基准上评估了训练后的 Qwen3-8B 模型：PyTorch-to-HIP、TritonBench-G 与 ROCmBench。实验采用固定评测预算，与多个对比模型进行比较。结果显示，该模型在 PyTorch-to-HIP 上取得 34.0% 的 Pass@1，在 TritonBench-G 上取得 33.2% 的 Corr@3，在 ROCmBench 上取得 41.94% 的 Corr@3，均为对比模型中的最高正确率。这表明基于 AMDKernelVault 语料库的 SFT 与执行感知 RL 能显著提升模型生成 AMD 内核的正确性。不过论文也指出，该模型在编译通过率与速度指标上并非全面领先，说明正确性与性能优化之间仍存在权衡，也为后续研究留下了改进空间。

优势与不足 ​

【优势与不足】

优势：

  • 首次构建面向 AMD CDNA GPU 的大规模执行验证内核语料库，填补了 CUDA 之外的数据空白，具有基础设施价值。
  • 智能体驱动流水线将生成、编译、验证、剖析整合，减少对闭源前沿 LLM 的反复调用，提升可复现性与成本效率。

不足：

  • 模型在编译通过率与速度指标上并非全面领先，说明正确性与性能优化尚未统一。
  • 语料库主要覆盖 CDNA 架构，对其他 AMD 架构或消费级 GPU 的泛化性有待验证。
  • 执行感知 RL 的奖励设计与训练成本细节披露有限，可能影响复现难度。
