问题的初衷（Why - 为什么要做这个研究） ​

【问题的初衷】检索增强生成（Retrieval-Augmented Generation, RAG）系统已成为缓解大语言模型（Large Language Model, LLM）幻觉、提升事实准确性的主流范式，其典型流水线由检索器（Retriever）、向量数据库（Vector Database）、提示处理（Prompt-Processing）与生成器（Generator）等多个阶段串联而成。然而，现有 RAG 评测工作存在三方面显著不足：第一，评测维度单一，多数基准只关注最终答案质量（如 EM、F1），忽视了延迟、吞吐、显存占用、功耗等系统级指标，导致研究者无法定位真正的性能瓶颈；第二，评测粒度粗糙，缺乏对每个阶段（检索、重排、压缩、预填充、解码）的细粒度计时与资源监控，难以揭示跨阶段交互效应；第三，评测成本高昂，每次配置变更都需重新初始化模型与数据库，使得在大配置空间（检索深度、模型规模、重排策略、压缩方法、向量库类型）上的系统性扫描几乎不可行。在中小规模多 GPU 环境下，这种评测空白尤为突出：研究者既缺乏可复现的基准，也缺乏能指导工程取舍的数据。因此，构建一个模块化、可扩展、能同时刻画质量与效率的 RAG 基准框架，对于推动 RAG 系统从“能用”走向“好用、省电、可部署”具有重要的现实意义。

问题的解决（What - 提出了什么方案） ​

【问题的解决】论文提出 RAGMark，一个面向小规模多 GPU 环境的模块化 RAG 基准测试框架。其核心思路是将 RAG 流水线解耦为可独立替换的阶段组件（检索器、向量数据库、提示处理方法、生成器），并将计时（Timing）与资源监控（Resource Monitoring）也抽象为独立模块，从而实现“组件可插拔、指标可组合、配置可扫描”。关键创新点有三：其一，通过复用已初始化的模型与数据库实例，避免在配置扫描中反复加载权重与重建索引，将单次实验开销从分钟级压缩到秒级，使大规模配置空间扫描成为可能；其二，引入逐阶段细粒度指标采集，包括每阶段延迟、GPU 利用率、显存消耗、功耗、首 token 时间（Time to First Token, TTFT）、吞吐量与答案质量，从而支持跨阶段瓶颈归因；其三，通过系统实验揭示了 RAG 流水线中的跨阶段交互规律——上下文压缩会把瓶颈从自回归生成转移到计算、内存带宽与预处理阶段，而重排与压缩具有复合收益，二者联合可将能耗降低最多 66%。与现有仅关注端到端质量或单一指标的基准相比，RAGMark 的本质区别在于把 RAG 评测从“黑盒打分”推进到“白盒剖析”，为系统优化提供可操作的证据链。

技术方法详解（How - 怎么实现的） ​

【技术方法详解】

  • 模块化阶段解耦：将 RAG 流水线拆分为检索、重排、压缩、提示构建、预填充、解码等阶段，每个阶段实现统一接口，支持任意替换与组合，便于消融实验。
  • 资源与计时监控层：独立于业务逻辑的监控模块，周期性采样 GPU 利用率、显存、功耗，并在阶段边界打点记录延迟，实现 Tstage 级别的细粒度归因。
  • 实例复用与配置扫描：模型权重与向量数据库索引在多次配置间复用，仅重建变化部分，将配置扫描复杂度从 O(N⋅Tinit) 降为 O(Tinit+N⋅Trun)，其中 N 为配置数。
  • 多维度指标采集：同时记录 TTFT、吞吐、端到端延迟、能耗与答案质量（EM/F1），支持质量-效率帕累托分析。
  • 跨阶段交互分析：通过控制变量扫描检索深度 k、模型规模、重排开关、压缩率与向量库类型，量化上游上下文缩减对下游延迟、内存流量与能耗的级联影响。
  • 可扩展插件机制：新增检索器或生成器只需实现对应接口，无需修改框架核心，保证长期可维护性与社区扩展性。

【核心公式】

Te2e=Tret+Trerank+Tcomp+Tprefill+Tdecode

该式表示端到端延迟由检索、重排、压缩、预填充与解码各阶段延迟之和构成，是逐阶段归因分析的基础。

具体技术细节示例（How in Action - 算法如何执行） ​

【具体技术细节示例】假设我们要评测一个开放域问答查询：“谁是《物种起源》的作者？”。配置为：检索深度 k=5，启用重排，启用压缩，生成模型为 7B 参数模型。

第一步，初始化阶段：框架加载 7B 模型权重并连接向量数据库，由于实例复用，此步骤仅在首次执行时耗时约 30 秒，后续配置扫描直接跳过。

第二步，检索阶段：查询被编码为向量，在向量数据库中执行近似最近邻搜索，返回 5 篇候选文档，耗时 Tret=12 ms，GPU 利用率约 15%。

第三步，重排阶段：使用交叉编码器对 5 篇文档打分并排序，保留前 3 篇，耗时 Trerank=45 ms，显存增加 0.8 GB。

第四步，压缩阶段：对 3 篇文档进行上下文压缩，将总 token 数从 1800 压缩到 600，耗时 Tcomp=28 ms，此阶段主要受内存带宽限制。

第五步，预填充阶段：将压缩后的 600 token 提示输入模型，执行预填充，耗时 Tprefill=90 ms，TTFT 为 90 ms。

第六步，解码阶段：自回归生成答案“查尔斯·达尔文”，共生成 8 个 token，耗时 Tdecode=160 ms，吞吐约 50 token/s。

第七步，指标聚合：端到端延迟 Te2e=12+45+28+90+160=335 ms，总能耗由各阶段功耗与时间乘积求和得到。对比不启用重排与压缩的朴素配置，其上下文为 1800 token，预填充与解码显著更长，端到端延迟可能超过 600 ms，能耗高出约 60%。该示例直观展示了上游上下文缩减如何级联降低下游预填充与解码成本。
